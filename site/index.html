Version control that lives in your bucket.

A pail repository is just a folder in S3, GCS or any other object store. There's no server, and there's no push. When you commit, pail uploads a few new files and does one conditional write to the branch, and everyone sees the commit right away. pail log and pail show print exactly what Git would.

$ pail init gs://your-bucket/app

How it works

Nothing in the bucket changes except the branch pointers.

File contents go into packs. The file tree of each commit is a prolly tree, split into small pages named by their BLAKE3 hash. Change three files and you write three or four small pages, whether the repository has a hundred files or a million. Commits, pages and packs are never modified after they're written, so you can cache them anywhere.

The only thing that ever changes is refs/<branch>, and only through compare-and-swap. Every major object store supports that kind of conditional write now. That one write is the commit.

refs/main the branch: {commit, version}, only moved by CAS
refs/pr/hello
commits/7f3a… parent, root, author, message, changed paths
pages/c684… manifest: path → size, hash, location
packs/91be….pack file contents, zstd
chunks/… large files, content-defined chunks
intents/main/… commits waiting to be combined

  1. Prepare locally. pail hashes the changed files, rebuilds the few pages above them and writes the commit object. It knows the name of everything it's going to upload before it sends a byte.

  2. Upload everything at once. Packs, pages and the commit go up in parallel, so that's one round trip.

  3. Move the branch. One conditional write, from the version your working copy last saw. That's the second round trip. If someone else got there first and touched different files, pail replays your commit on top of theirs.

  4. When it's busy, batch. A writer that loses the race leaves an intent instead of retrying. The oldest waiting writer lands all pending intents in one write, each as its own commit, in order. This matters on GCS, which only allows about one write per second to the same object.

Numbers

How it compares to pushing to GitHub

We ran the same edits through both CLIs from the same laptop. Each writer made 20 commits to one shared branch: git add/commit/push to a private GitHub repository, and pail add/commit to a GCS bucket. After each pail run we checked that every commit actually made it onto main.

A caveat: this was a home connection in Phoenix in October 2026, about 90 ms from github.com and 35 ms from storage.googleapis.com. Both tools spend most of their time waiting on round trips, so both get faster from a machine in the bucket's region. Calling pail as a library, without starting a process per commit, got to 7.1 commits per second with 16 writers.

Agents

Built for lots of agents committing to the same branch

Land a whole stack at once

pail land feature --stack puts every commit on a branch onto main in one write. If it fails partway, run it again. It picks up where it left off.

Cheap worktrees

Working copies are copy-on-write clones of one shared cache. Build output gets cloned too, so a new worktree starts with a warm build and doesn't double your disk usage.

Same output as Git

pail log, show, cat-file and ls-tree take Git's flags and print Git's output. We mirror our own monorepo into pail as it changes and check every commit byte for byte. Thousands of commits so far, no mismatches.

Your data stays in your bucket

Nothing leaves your cloud account. People don't need bucket keys either: a credential provider hands out short-lived tokens that only work for one repository.

Real conflicts stop you

Changes to different files just work. When two writers change the same file, the second one gets exit code 4 and a list of the files, so a script or an agent knows exactly what to sync.

Hooks run before anything lands

pre-commit, commit-msg and pre-publish all run before the branch moves. pre-publish sees the exact commit that's about to land.

Extend

PRs and CI are just programs that read and write branches

You don't need a server for pull requests or CI. Every commit is a write to refs/<branch>, and object stores already send a notification when something is written. A tool listens for those, reads what it needs, and saves its results as commits on a _meta branch. That way every record gets history and conflict checks for free.

NameMeaning
pr/*Branches proposed for review.
_meta:prs/12.jsonA pull request: title, head, base, author, state. Claimed once with pail put --if-absent.
_meta:prs/12/reviews/bob.jsonA review: approve or request changes.
_meta:checks/<commit>/test.jsonA check result for one commit, written by CI.
main:pail.ci.jsonThe checks a commit declares, and which are required to merge.
 
# wire the bucket's notifications once
gcloud storage buckets notifications create gs://acme-vcs \
  --topic=pail-refs --object-prefix=app/refs/

# CI: follow ref events, build the exact commit,
# record each check on _meta
pail-ci run --branch 'pr/*' \
  --gcs-subscription projects/acme/subscriptions/pail-ci

# under the hood: plain pail commands
pail events --branch 'pr/*'
pail clone gs://acme-vcs/app src --at 126ebf48
pail put _meta --file checks/126ebf48/test.json=-
pail switch -c pr/hello
pail commit -am "Say hello"
pail-pr open pr/hello --title "Say hello"
opened PR 1: pr/hello → main

pail-pr review 1 --approve       # as Bob
pail-pr merge 1
landed 1 commit(s) from pr/hello onto main
merged PR 1 into main @ 126ebf48d9dc

Both are short scripts that only call the pail CLI. On GCS, the notification showed up 1.2 to 1.6 seconds after the commit started. Notifications can arrive twice or out of order, so pail events re-reads the branch and drops duplicates, and CI files every result under the commit it tested.

Protect branches

The bucket itself enforces branch protection

There's no server in the middle, so a rule only means something if the object store enforces it. That's where pail puts it. Only a lander can write a protected branch. Everyone else can add history but never delete or rewrite it, and the lander only moves refs/main once the reviews and checks pass.

ObjectPeople and agentsLanderWhy
refs/main, refs/release/*readwriteProtected branches only move after review.
refs/pr/*, refs/<you>/*writewriteWork in progress doesn't wait on anyone.
commits/ pages/ packs/create onlycreate onlyNobody can delete or rewrite history. Only garbage collection deletes.
intents/main/*nonewriteNo batching on protected branches (more below).
_policyreadadmins onlyOnly admins can change the rules.
 
# _policy:policy.json  (pail policy set)
{ "version": 1, "admins": ["role:admin"], "branches": {
  "main": {
    "writers": ["lander"],
    "approvals": 1,
    "required_checks": ["test", "lint"]
  },
  "release/*": { "writers": ["lander"], "approvals": 2 },
  "_policy": { "writers": ["role:admin"] },
  "*": { "writers": ["*"] }
} }

  1. Sign in and get a token. A broker checks who you are and runs pail policy token --as you. The token it hands back is short-lived and only allows what the policy allows, so committing straight to main fails at the bucket.

  2. Commit to a PR branch. Commits to pr/* work like any other commit. CI hears about them from the bucket's notifications and records its checks.

  3. Get a review. An approval is a record for one exact commit. A review tool writes it and stamps who actually signed in, so you can't approve in someone else's name.

  4. The lander merges. The lander is the only identity that can write refs/main. It reads pail policy requirements main, makes sure someone other than the author approved and the required checks passed on that exact commit, and then lands the stack in one write.

Where the rules are checked

The same policy file works three ways. pail serve checks every request, on any backend. A broker runs pail policy token so GCS enforces it directly. The lander checks reviews and CI before it moves a branch.

No batching on protected branches

When pail batches commits, the writer doing the batching lands everyone else's changes too. On main, that would be a way to sneak in unreviewed work. So only the lander writes there, and it only batches changes it has already approved.

The author field isn't trusted

A commit's author is whatever the writer typed in. Policy decisions only look at who actually authenticated, or at records a trusted tool wrote. They never look at the author field.

We tested this on GCS. A token built from these rules can read the repository, add history and write refs/pr/*. It gets a 403 when it tries to write refs/main or refs/release/*, delete or overwrite history, or touch another repository. One requirement: people can't have bucket permissions of their own. They only get tokens from the broker. docs/protecting-branches.md explains how to build the broker and the lander.

Get started

All you need is a bucket

Any S3 or GCS bucket works, or a local folder with file://. People who don't have bucket credentials can sign in through a credential provider, or go through pail serve.

pail init gs://acme-vcs/app
pail clone gs://acme-vcs/app && cd app
pail add -A
pail commit -m "First commit"   # published
pail log --oneline
