Version control that lives in your bucket.

A pail repository is a prefix in S3, GCS or any object store. There is no server and no push: a commit is new immutable objects plus one conditional write to its branch, so every clone sees it at once. History reads as Git, byte for byte.

$ pail init gs://your-bucket/app

How it works

Everything is immutable except the branch pointers.

File contents go into packs, and the tree of every commit is a prolly-tree manifest: pages named by their BLAKE3 hash, so a commit that changes three files writes three or four small pages no matter how large the repository is. Commits, pages and packs are never modified, which makes them safe to cache anywhere.

The only object that ever changes is refs/<branch>, and it changes only by compare-and-swap, the conditional write every major object store now supports. That one write is the commit.

refs/main the branch: {commit, version} · moved only by CAS
refs/pr/hello
commits/7f3a… parent, root, author, message, changed paths
pages/c684… manifest: path → size, hash, location
packs/91be….pack file contents, zstd
chunks/… large files, content-defined chunks
intents/main/… commits waiting to be combined

  1. Prepare locally. Hash the changed files, rebuild the few pages on their path, encode the commit. Every object's name is known before anything is sent.

  2. Upload in one wave. Packs, pages and the commit object go up in parallel: one round trip.

  3. Swap the branch. One conditional write from the version this working copy last saw: the second round trip. If another writer got there first on different files, pail replays the commit on the new head automatically.

  4. Under contention, combine. A writer that loses publishes an intent; the oldest waiting writer lands every pending intent with one swap, each as its own commit, in order. On GCS, which allows about one write per second to an object, batches grow with the load instead of the swap rate.

Built for agent fleets

Many writers, one history, no queue.

Stacks land atomically

pail land feature --stack puts every commit of a branch onto main in one swap, fast-forward or replayed. Run it again after a failure; it is idempotent.

Worktrees cost almost nothing

Working copies are copy-on-write clones of one shared content cache, and ignored build output is cloned from the current copy, so a new worktree starts warm without doubling the disk.

Git reads it

pail log, show, cat-file and ls-tree take Git's options and print Git's output. A live mirror proves every commit of a real monorepo byte for byte.

Your bucket, your account

Data never leaves your cloud. Credential providers mint short-lived tokens scoped to one repository, so people need no bucket keys of their own.

Conflicts are explicit

Disjoint changes replay on their own. When two writers change the same path, the later one gets exit code 4 and the path list, and syncs.

Hooks where they belong

pre-commit, commit-msg and pre-publish run before the swap; the pre-publish hook checks the exact commit that will land.

Extend

Features are programs that agree on names.

Pull requests and CI need no server here. Every publish is a write to refs/<branch>, and object stores already announce writes. A tool subscribes to those notifications, reads what it needs, and records results as commits on a _meta branch, which makes every record atomic, versioned and conflict-checked.

NameMeaning
pr/*Branches proposed for review.
_meta:prs/12.jsonA pull request: title, head, base, author, state. Claimed once with pail put --if-absent.
_meta:prs/12/reviews/bob.jsonA review: approve or request changes.
_meta:checks/<commit>/test.jsonA check result for one commit, written by CI.
main:pail.ci.jsonThe checks a commit declares, and which are required to merge.
 
# wire the bucket's notifications once
gcloud storage buckets notifications create gs://acme-vcs \
  --topic=pail-refs --object-prefix=app/refs/

# CI: follow ref events, build the exact commit,
# record each check on _meta
pail-ci run --branch 'pr/*' \
  --gcs-subscription projects/acme/subscriptions/pail-ci

# under the hood: plain pail commands
pail events --branch 'pr/*'
pail clone gs://acme-vcs/app src --at 126ebf48
pail put _meta --file checks/126ebf48/test.json=-
pail switch -c pr/hello
pail commit -am "Say hello"
pail-pr open pr/hello --title "Say hello"
opened PR 1: pr/hello → main

pail-pr review 1 --approve       # as Bob
pail-pr merge 1
landed 1 commit(s) from pr/hello onto main
merged PR 1 into main @ 126ebf48d9dc

Both extensions are short programs that only call the pail CLI. Measured on GCS, a ref event reached the subscriber 1.2 to 1.6 seconds after the commit started. Notifications are at-least-once and unordered, so pail events re-reads the ref and drops duplicates, and CI keys every result by commit.

Protect branches

The bucket's permissions are the rule book.

With no server in the write path, a rule only holds if the store enforces it. So pail puts protection where the bytes are: nobody but a lander can write a protected ref, content is create-only, and the lander moves refs/main only after the policy is met.

ObjectPeople and agentsLanderWhy
refs/main, refs/release/*readwriteProtected branches move only through review.
refs/pr/*, refs/<you>/*writewriteWork in progress stays fast and unreviewed.
commits/ pages/ packs/create onlycreate onlyHistory cannot be deleted or overwritten. Only GC deletes.
intents/main/*nonewriteNo combining on a protected branch (see below).
_policyreadadmins onlyThe rules themselves are protected.
 
# _policy:branches.json
{
  "main": {
    "writers": ["lander"],
    "approvals": 1,
    "required_checks": ["test", "lint"],
    "code_owners": "main:CODEOWNERS"
  },
  "release/*": { "writers": ["lander"], "approvals": 2 },
  "pr/*": { "writers": ["*"] }
}

  1. Sign in, get a narrow token. Your credential provider mints a short-lived token for one repository. Its access boundary leaves out protected refs and every delete, so a direct push to main fails at the bucket.

  2. Push to a PR branch. Commits land on pr/* as usual; CI records checks from the bucket's events.

  3. Reviews are signed. An approval is an attestation signed by the identity service ("bob approved 126ebf48"), so no one can write a review in someone else's name.

  4. The lander merges. A merge request is an event. The lander, the only identity allowed to write refs/main, checks approvals from people other than the author, required checks on the exact head commit and code owners, then lands the stack with one swap.

Three places to enforce

Bucket IAM for the floor (create-only content, no deletes). A token broker plus lander for repositories in your own bucket, with no server in the path. Or a gateway such as ArchDev's, which checks every request against the branch rules.

No combining across trust

Combining lands other writers' changes with the combiner's permissions. On a protected branch that would let a privileged writer land unreviewed work, so only the lander writes there, and it batches only changes it approved.

Authors are claims, signatures are proof

A commit's author field says who the writer typed in. Policy decisions rely only on authenticated writers or signed records, never on that field.

Status: today, credential providers already mint tokens scoped to one repository prefix (verified on GCS), and the PR prototype checks approvals and required checks before landing. Next: the policy file, the lander, signed reviews, and per-ref token boundaries.

Get started

One bucket, one command.

Any S3, GCS or file:// location works. People without bucket credentials sign in through a credential provider, or reach the repository through a proxy.

pail init gs://acme-vcs/app
pail clone gs://acme-vcs/app && cd app
pail add -A
pail commit -m "First commit"   # published
pail log --oneline
